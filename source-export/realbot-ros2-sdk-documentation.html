1. Project Overview

The RealHand ROS2 SDK’s nodes construct hand and arm objects from the separately installed realhand Python SDK, adapt their methods to ROS operations, and expose commands and feedback through sensor_msgs/msg/JointState and std_msgs/msg/String.

The following model identifiers are used in this document:

Device family

Model values used in this document

Command width

Dexterous hand

L6, O6

6 values

Dexterous hand

L20

16 values

Arm

P7, A7lite

7 values

1.1 Runtime capability boundaries

Repository-verifiable consequences:

  • Hand metadata confirms command widths and joint order: L6 and O6 use six values, while L20 uses sixteen values.

  • The touch publisher receives the same force_sensor payload as the force_sensor publisher.



The delivered user-facing capabilities are:

  • single-hand and dual-hand ROS 2 backends;

  • typed sensor_msgs/msg/JointState command and state topics;

  • A7lite and P7 arm ROS 2 backends;

  • JSON command, sensor, device-information, control-status, and blocking-result topics;

  • SDK polling, event streaming, cached snapshots, and asynchronous blocking reads;

  • a PyQt GUI for hand and arm operation;

  • automated installation helpers and focused example scripts.

2. Software Architecture

The package uses a layered design:

2.1 Layer responsibilities

Layer

Implementation

Responsibility

Model metadata

hand/model.py, arm/model.py

Normalizes model names, defines joint order, and lazily resolves external SDK classes.

Adapter

hand/adapter.py, arm/adapter.py

Converts Python SDK objects and sensor records into plain lists/dictionaries and wraps device operations.

ROS bridge

hand/node.py, arm/node.py

Declares parameters, creates topics and timers, translates messages, and owns adapter lifetime.

GUI ROS facade

gui/ros_client.py

Publishes commands and subscribes to selected feedback topics for the active side.



2.2 Threading and concurrency

  • Backend ROS callbacks and periodic timers are handled by the rclpy spin executor started with rclpy.spin(node).

  • The GUI's main ROS client uses a Qt QTimer to call rclpy.spin_once(..., timeout_sec=0.0).

  • Hand sensor streaming uses a background Python thread to consume the SDK event queue.

  • Each get_blocking request runs in its own background thread so the ROS callback is not blocked.

  • GUI auto-detection runs in a separate thread or Qt worker thread.

  • Stopping a stream requests SDK stream shutdown and waits up to one second for the consumer thread to finish.

5.1 Manual installation

sudo apt update

sudo apt install -y \

can-utils \

python3-pip \

python3-colcon-common-extensions \

python3-pyqt5

Source ROS 2 and install a compatible RealHand Python SDK into the same Python environment used by ROS 2.

5.2 Automated installation

From the current checkout, install dependencies and build a workspace with one of these repository-provided commands:

./install.sh --workspace ~/realhand_ros2_ws
./install.sh --install-ros --workspace ~/realhand_ros2_ws
./install.sh --with-arm --workspace ~/realhand_ros2_ws

Ubuntu 22.04 maps to ROS 2 Humble and Ubuntu 24.04 maps to ROS 2 Jazzy by default. Set ROS_DISTRO explicitly to override the detected default. Use --local-sdk PATH for an editable local RealHand Python SDK checkout.

A7lite kinetix support requires the Python SDK's optional kinetix dependencies, selected by --with-arm. P7 uses the RBot TCP controller and does not require the kinetix extra.

Ubuntu 24.04 uses an externally managed system Python. For direct system-Python installation, the repository adds --break-system-packages and --ignore-installed; do not use pip to upgrade the system pip on Ubuntu 24.04.



6. Workspace Setup

Use a conventional ROS 2 workspace layout:

mkdir -p ~/realhand_ros2_ws/src
cd ~/realhand_ros2_ws/src
git clone https://github.com/RealHand-Robotics/realbot-ros2-sdk.git
cd ..

If working from an existing local checkout, copy only source-controlled content. Do not carry old build/, install/, log/, .pytest_cache/, __pycache__/, or *.egg-info/ artifacts into the new workspace.

Every new terminal must source the ROS distribution and, after building, the workspace overlay:

source /opt/ros/humble/setup.bash
source ~/realhand_ros2_ws/install/setup.bash

Optional shell convenience:

echo 'source /opt/ros/humble/setup.bash' >> ~/.bashrc
echo 'source ~/realhand_ros2_ws/install/setup.bash' >> ~/.bashrc

7. Build Instructions

From the workspace root:

source /opt/ros/humble/setup.bash
cd ~/realhand_ros2_ws
colcon build --symlink-install --packages-select realhand_ros2
source install/setup.bash

Validate the installation:

ros2 pkg prefix realhand_ros2
ros2 pkg executables realhand_ros2

setup.py defines these executable names:

realhand_ros2 realhand_arm_node
realhand_ros2 realhand_gui
realhand_ros2 realhand_hand_node

7.1 Run package tests

cd ~/realhand_ros2_ws
colcon test --packages-select realhand_ros2
colcon test-result --verbose

Current automated coverage is limited to part of the model metadata. Within this guide's scope it checks L6 and L20 hand joint counts, A7lite and P7 arm joint counts, and P7's default interface name and interface type. The repository does not include complete hardware communication, topic integration, launch, GUI, or end-to-end tests.

7.2 Clean rebuild

When stale generated metadata or an old copied checkout causes discovery problems, remove only the generated workspace directories from the workspace root, then rebuild:

cd ~/realhand_ros2_ws
rm -rf build install log
source /opt/ros/humble/setup.bash
colcon build --symlink-install --packages-select realhand_ros2
source install/setup.bash

8. Running the SDK

8.1 Prepare SocketCAN

HandNode defaults to can0/socketcan. The A7lite arm model also defaults to can0/socketcan. Backend nodes pass the selected interface values to adapter constructors and do not execute ip link configuration commands.

sudo ip link set can0 down
sudo ip link set can0 type can bitrate 1000000
sudo ip link set can0 up
ip -details link show can0

Useful diagnostics:

ip link show
candump can0

8.2 Start a hand backend

source /opt/ros/humble/setup.bash
source ~/realhand_ros2_ws/install/setup.bash
ros2 launch realhand_ros2 hand.launch.py \
model:=L6 side:=left interface_name:=can0

8.3 Start two hands

ros2 launch realhand_ros2 dual_hand.launch.py \
model:=L6 left_interface:=can0 right_interface:=can1

This launches two realhand_hand_node processes named realhand_left_hand_node and realhand_right_hand_node. Both use the same model argument but different side and interface values.



8.4 Start the GUI

ros2 launch realhand_ros2 gui.launch.py

run_gui.sh verifies /opt/ros/$ROS_DISTRO/setup.bash and the repository-local install/setup.bash, sources both, and executes the GUI launch file. It defaults to Humble.

The GUI is initially a ROS client. Use Start Backend on the applicable tab to launch a matching GUI-owned backend, or run the backend separately before opening the GUI. Stop Backend stops the GUI-owned backend process.

8.5 Confirm the ROS graph

ros2 node list
ros2 topic list | grep realhand
ros2 node info /realhand_hand_node

10. ROS 2 Nodes

10.1 Hand bridge node

Item

Description

Purpose

Exposes one supported RealHand hand through typed command/state and JSON control/sensor topics.

Executable

realhand_hand_node

Default node name

/realhand_hand_node

Input topics

/{prefix}/command (JointState) and /{prefix}/command_json (String).

Output topics

Joint state, snapshot, device information, sensor data, blocking results, and control status.

Parameters

Model, side, interface, connection, state/poll/stream settings, and command, state, sensor, and status topic overrides.

Typical use

Publish position, speed, torque, polling, stream, snapshot, blocking-read, and fault-clear commands and subscribe to feedback.



Typed Hand JointState fields are processed in this source order: velocity -> HandAdapter.set_speeds(), effort -> HandAdapter.set_torques(), then position -> HandAdapter.set_angles(). JointState.name is informational and is not used to reorder arrays.

Hand JSON processing order is action -> speeds -> torques -> angles. The command field is speeds (plural). An unknown non-empty action raises an unsupported hand JSON action error before array fields are processed.

All HandNode publishers are created for every instance, but optional sensor data depends on the selected model and installed RealHand Python SDK.

Sensor Polling, Event Streaming, and Blocking Reads

The periodic ROS state timer, SDK polling, SDK event stream, and one-shot blocking reads are separate mechanisms:

Mechanism

Execution

Output / control

Periodic ROS state timer

Runs at state_rate_hz; reads the cached snapshot and force-sensor data.

Publishes Hand JointState, snapshot JSON, and related sensor topics.

SDK polling

Provided by the external SDK. poll_on_start defaults to true; intervals come from poll_intervals_json or start_polling.

start_polling/stop_polling; supported sensors depend on model and installed SDK.

SDK event stream

stream_on_start defaults to true; a background thread consumes an SDK queue whose default maxsize is 300.

Events are routed by type; start_stream/stop_stream control the stream.

Blocking read

Each get_blocking request runs once in a separate background thread.

Result is published asynchronously on blocking_result; it is not a ROS service.

Explicit unsupported polling sensors can return an error. Stopping the stream requests SDK shutdown and waits a finite time for its consumer thread. With pause_polling=true, a blocking read may stop polling temporarily and restore the prior intervals afterward.

10.2 Arm bridge node

Item

Description

Purpose

Exposes one arm through ROS 2 topics.

Executable

realhand_arm_node

Default node name

/realhand_arm_node

Input topics

/{prefix}/joint_command (JointState) and /{prefix}/command_json (String).

Output topics

std_msgs/msg/String

The node creates all listed publishers. Optional sensor publishers emit only when the selected model and installed RealHand Python SDK provide data. /hand/touch is an alias publication of the force-sensor payload, not an independent sensor format.

device_info JSON contains available, model, side, interface_name, interface_type, serial_number, firmware_version, mechanical_version, pcb_version, timestamp, and, when unavailable, error. An unavailable device-info read can still publish available=false with empty version fields and an error.

blocking_result payloads follow the source result envelope: action, sensor, request_id, timestamp, ok, and data or error; get_blocking additionally reports timeout_ms and pause_polling. control_status reports acknowledgements and state for explicitly handled polling and streaming control paths. Its payload includes action, ok, timestamp, streaming, polling status, and action-specific fields such as intervals, maxsize, accepted, request_id, sensor, timeout_ms, or error. It is not a universal error channel: most JSON parsing or command-execution exceptions are written only to the ROS log, while get_snapshot and get_blocking results, including errors, are published on blocking_result. An unsupported start_stream operation is an explicit example that publishes control_status with ok=false and an error.

Arm joint ordering

13.2 JSON carried in std_msgs/msg/String

The data field contains one JSON value. Command handlers expect a JSON object. Sensor serialization recursively handles dataclasses, Pydantic-like model_dump(), NumPy-like tolist(), SDK to_list(), dictionaries, lists, tuples, primitives, and finally repr().

Hand JSON commands

Payload field/action

Effect and validation

speeds

Calls set_speeds; processed after action.

torques

Calls set_torques; processed after speeds.

angles

Calls set_angles; processed after torques.

action: clear_faults

Calls the adapter fault-clear operation. Availability depends on the selected model and installed RealHand Python SDK.

action: start_polling

Optional intervals must be a JSON object; every value must convert to float and be > 0. Explicit unsupported sensors may return an error.

action: stop_polling

Stops SDK polling and publishes status on control_status.

action: start_stream

Optional maxsize is converted to an integer and must be positive; starts background SDK-event consumption.

action: stop_stream

Requests SDK stream stop, ends the consumer thread, and publishes status.

action: get_snapshot

Optional sensor and request_id; publishes the result on blocking_result.

action: get_blocking

Requires sensor; accepts timeout_ms, pause_polling, and request_id; runs in a worker thread and publishes asynchronously on blocking_result.

A single Hand JSON object is handled in the order action -> speeds -> torques -> angles. Unknown non-empty actions are errors, so their array fields are not reached. Supported sensors and fault/poll/stream operations depend on the selected model and installed RealHand Python SDK.

Arm JSON commands

Payload field/action

Effect

velocities

Calls set_velocities; processed first.

accelerations

Calls set_accelerations; processed second.

action: enable

Calls enable().

action: disable

Calls disable().

action: home

Calls home(blocking=...).

action: reset_error

Calls reset_error().

action: emergency_stop

Calls emergency_stop(enable); enable defaults to true.

action: resume_from_emergency_stop

Uses SDK resume_from_emergency_stop() when available, otherwise emergency_stop(False); raises an unsupported-resume error if neither exists.

joints

Calls move_j(values, blocking=...); processed after action.



Arm JSON order is velocities -> accelerations -> action -> joints. Thus motion settings are applied before an action, and joints are handled afterward. home and joints accept blocking; emergency_stop accepts enable. Use true JSON booleans: do not send the string "false", because Python bool("false") is true. An unknown action itself is ignored, while recognized velocities, accelerations, and joints in the same object still execute.

14. API Usage

14.1 Publish a typed hand command

python3 examples/send_hand_command.py --model L6 --side left --positions 50,50,50,50,50,50
python3 examples/send_hand_command.py --model L6 --side left --velocities 40,40,40,40,40,40
python3 examples/send_hand_command.py --model L6 --side left --torques 30,30,30,30,30,30

If a typed command contains all three arrays, the backend applies velocity, then effort, then position. Arrays must follow the selected model's implementation order; name is informational, and the ROS node adds no clamping or vector-length validation.

14.2 Hand JSON control and reads

The example publisher accepts raw JSON and exposes every Hand action:

python3 examples/send_hand_command.py --side left --json '{"action": "clear_faults"}'
python3 examples/send_hand_command.py --side left --json '{"action": "start_polling", "intervals": {"angle": 0.03333333333333333}}'
python3 examples/send_hand_command.py --side left --json '{"action": "stop_polling"}'
python3 examples/send_hand_command.py --side left --json '{"action": "start_stream", "maxsize": 300}'
python3 examples/send_hand_command.py --side left --json '{"action": "stop_stream"}'
python3 examples/send_hand_command.py --side left --json '{"action": "get_snapshot", "sensor": "angle", "request_id": "angle-cache-1"}'
python3 examples/send_hand_command.py --side left --json '{"action": "get_blocking", "sensor": "fault", "timeout_ms": 500, "pause_polling": true, "request_id": "fault-1"}'

get_snapshot and get_blocking publish results on /realhand/left/hand/blocking_result. get_blocking is asynchronous topic-based processing, not a synchronous ROS service.

14.3 Arm startup and movement

# Start model-correct backends.
./examples/start_backend.sh arm A7lite left can0
./examples/start_backend.sh arm P7 left 192.168.10.21 rbot

# Enable the arm.
python3 examples/arm_enable_disable.py --side left enable

# Set velocity and acceleration.
python3 examples/arm_set_velocity_acceleration.py --model P7 --side left \
--velocities 0.5,0.5,0.5,0.5,0.5,0.5,0.5 \
--accelerations 1,1,1,1,1,1,1

# Execute move_j; motion settings in this JSON object run first.
python3 examples/arm_move_j.py --model P7 --side left \
--joints 0,0,0,0,0,0,0 \
--velocities 0.5,0.5,0.5,0.5,0.5,0.5,0.5 \
--accelerations 1,1,1,1,1,1,1

Arm command processing is velocity -> acceleration -> position for typed JointState, and velocities -> accelerations -> action -> joints for JSON. Position movement uses non-blocking move_j for typed commands.

14.4 Arm state and emergency-stop examples

python3 examples/arm_read_state.py --side left
python3 examples/arm_emergency_stop.py --side left
python3 examples/arm_enable_disable.py --side left resume_from_emergency_stop
bash examples/arm_move_then_emergency_stop.sh left 0.5

arm_read_state.py reads joint_state and pose. The final shell example sends a move command and triggers emergency_stop after the requested delay.

14.5 Direct adapter API

The adapters are importable Python classes:

from realhand_ros2.hand import HandAdapter

hand = HandAdapter(
model="L6",
side="left",
interface_name="can0",
interface_type="socketcan",
)
try:
hand.set_speeds([40] * 6)
hand.set_torques([30] * 6)
hand.set_angles([50] * 6)
print(hand.snapshot_payload())
finally:
hand.close()

15.2 Dual-hand operation

Launch dual_hand.launch.py, then inspect the two topic namespaces:

The provided dual launch supports a common model only. For different left/right models, start two hand.launch.py processes with distinct model, side, and interface arguments.

15.3 GUI hand workflow

The GUI checks for changed hand positions every 100 ms and publishes only when values differ; preset and home actions publish immediately. Auto Grab uses per-finger baseline subtraction and two-sample threshold debounce.

15.4 Slip detection and torque boost

The GUI computes touch magnitude change and pressure-centroid displacement. When both configured thresholds are crossed outside the cooldown window, it marks a slip. Optional torque boost increments command values for joints mapped to that finger and clamps them to 100.

15.5 Polling, streaming, snapshots, and blocking reads

Use start_polling/stop_polling for SDK polling, start_stream/stop_stream for the SDK event queue, and watch control_status for acknowledgements and state. Use get_snapshot for a cached read and get_blocking for a one-shot asynchronous blocking read whose result arrives on blocking_result. Sensor availability depends on the model and installed RealHand Python SDK.

16. Troubleshooting

16.1 Command fails or moves unexpected joints

  • Confirm model and array length.

  • Use the exact implementation-defined order in Section 13.

  • Do not assume JointState.name causes reordering; it does not.

  • Remember that arm command effort means acceleration.

17. Frequently Asked Questions (FAQ)

Does JointState.name determine command ordering?

No. Both backend callbacks pass numeric arrays directly. Use the exact order for the selected model.

What does JointState.effort mean?

For hand commands it is torque. For hand state it is the cached torque vector. For arm commands it is acceleration. For arm state it is the SDK torque reading.

Can I use different models in dual_hand.launch.py?

No. That launch file has one common model argument. Launch two single-hand instances for mixed models.

Can I change parameters at runtime?

The nodes read operational parameter values during construction and do not register a parameter-change callback.

How do I select right-side topics?

Launch with side:=right and use /realhand/right/.... The GUI recreates its topics when the side selection changes.

Can I disable hardware connection for graph testing?

Yes, when running the node directly, set connect_on_start:=false. Topics exist and commands are ignored with warnings, but no simulated state is published.
